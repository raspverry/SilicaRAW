# Task 18.5.2: Batch Sync History

## Goal

Apply validated edit subsets across selected photos with one undoable history checkpoint per affected photo.

- `apps/desktop/src-tauri/src/main.rs`

## Scope

- Apply selected edit subsets to multiple catalog photos.
- Record one undoable checkpoint per affected photo.
- Keep redo invalidation consistent with Phase 16 rules.
- Preserve originals, source identity, and sidecar explicit-write policy.
- Do not add collection-wide background jobs, plugin/MCP access, or automatic sidecar writes.

## Acceptance Criteria

- Batch sync validates every target before commit.
- Partial failure behavior is deterministic and documented by tests.
- Each affected photo has its own undoable history row.
- Original files remain unchanged.

## Completion Notes

- Core exposes a read-only batch sync plan boundary and an apply boundary for typed edit clipboard payloads.
- Storage commits ready target edit graphs through one SQLite transaction, not a loop of per-photo commits.
- If any target is blocked during preflight, the result is `blocked` and no `edit_states` or `edit_history` rows are written.
- Unchanged targets are skipped and do not receive history rows.
- Successful sync writes one `edit_history` `edit_commit` row per affected photo and invalidates redo per affected photo.
- Clean/in-sync sidecar status for affected photos becomes `catalog_newer`; sidecar files are not written or rewritten.
- Unsupported runtime paths remain blocked before write. Current blocks include non-neutral Detail payloads, unsupported Lens/Geometry payloads, and unsupported Basic runtime fields (`texture`, `clarity`, `dehaze`).

## Validation

## Stop Gates

Stop if batch sync cannot be expressed as catalog transactions with clear per-photo history.
