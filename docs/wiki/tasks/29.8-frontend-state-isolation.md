# Task 29.8: Frontend State Isolation

## Goal

After Task 29.7, replace implicit module-global frontend state with explicit per-screen state objects and, only where backend responses must be visible across screens, the smallest shared response mirror; document state ownership and transitions; and preserve current behavior, including the stale-preview monotonic guard, session restore, and keyboard and dialog state.

- The frontend modules produced by Task 29.7; do not assume Task 29.7 provides focused frontend state tests

## Files

- Exactly one new dependency-free executable state-transition contract harness under `scripts/harness/`; choose its exact filename during implementation and record its path and command in Completion State
- `scripts/harness/check.sh`, only to invoke the new contract harness
- `scripts/harness/check-static-ui.py`, only if its structural assertions must follow the state extraction
- `scripts/harness/check-ui-workflow-smoke.py`, only if its behavior-preserving assertions must follow the state extraction

## Scope

- Dependency: Task 29.7 must be complete and its frontend module boundaries must be stable before Task 29.8 begins.
- Replace implicit mutable module globals with explicit per-screen state objects that own only transient UI projections, navigation and dialog state, keyboard interaction state, and request sequencing.
- Keep Rust Core and the existing catalog, edit, and session persistence paths as the sole durable authority. Frontend state must not become a second catalog, edit graph, or session persistence source.
- Limit the shared store to the smallest read-only mirror of backend responses needed by more than one screen. Frontend actions must mutate durable state through existing backend commands and refresh the mirror from backend responses; the shared store must not author or persist domain state.
- Do not duplicate the same projection in a per-screen object and the shared response mirror.
- Document each state field's owner, readers, writers, initialization, reset point, and allowed transitions next to the state definitions.
- Route state changes through explicit transitions whose results are deterministic for the same initial state and ordered inputs.
- Establish exactly one smallest executable state-transition contract harness under `scripts/harness/` using only existing project execution facilities. It must exercise the production transition contract rather than reimplementing that logic in the harness.
- Keep contract coverage focused on two cases: deterministic replay of one concise transition sequence and rejection of an older preview response after a newer request or response. Do not turn this task into a broad frontend state test suite.
- Add no dependency or new runner for the harness. Record its exact path and invocation command in Completion State so Task 29.12 can reuse the same contract.
- Preserve the monotonic preview request guard so an older asynchronous response can never replace a newer preview.
- Preserve session restoration, screen navigation, selection, edit controls, keyboard handling, dialog open/close state, and all other existing frontend behavior.
- Use the framework-free frontend and existing dependencies only. Do not add a framework, state library, dependency, build system, fallback state path, or compatibility layer.
- Do not redesign the UI, change copy or styling, alter backend contracts, or combine unrelated frontend cleanup with this task.

## Acceptance Criteria

- Every task-owned mutable frontend state value has exactly one explicit owner and is limited to a transient UI projection, navigation or dialog state, keyboard interaction state, or request sequencing.
- Rust Core and the existing catalog, edit, and session persistence paths remain the sole durable authority; session restore and persisted edit or catalog values reach the frontend only through backend responses.
- The shared store only mirrors backend responses required across screens, never authors durable values, and contains no screen-local state promoted for convenience.
- State ownership, lifecycle, and allowed transitions are documented alongside the implementation.
- One dependency-free executable contract harness exists under `scripts/harness/`, exercises the production transition contract, and is invoked by the full harness.
- The contract harness proves only that replaying one concise initial-state and ordered-input sequence produces the same result and that an older preview response cannot supersede a newer request or response.
- Completion State records the contract harness's exact path and invocation command for reuse by Task 29.12.
- The stale-preview guard remains monotonic and deterministically rejects responses older than the latest accepted request.
- Existing session restore and UI workflow behavior remain unchanged, including selection, rating, pick/reject, preview, and Develop adjustment flows.
- Static UI and workflow smoke checks continue to pass without weakening assertions.
- The diff adds no framework, state library, dependency, runner, UI redesign, backend contract change, duplicate transition implementation, or unrelated refactor.

## Validation

- Run the executable state-transition contract harness directly with the exact command recorded in Completion State. Its assertions must remain limited to concise deterministic replay and stale-response rejection.
- Run the static and UI workflow smoke checks:

```bash
python3 scripts/harness/check-static-ui.py
python3 scripts/harness/check-ui-workflow-smoke.py
```

- Manually exercise screen navigation, session restore after relaunch, keyboard actions, dialog open/close behavior, rapid Develop adjustments, and return to the library grid without visible or behavioral regression.
- Run the full harness:

```bash
scripts/harness/check.sh
```

## Stop Gates

Stop if Task 29.7 is incomplete or its module boundaries are still changing; if frontend state must become a durable authority for catalog, edit, or session data; if the shared store must author domain state, contain screen-local state, or mirror anything other than backend responses; if state ownership requires duplicate sources of truth; if the stale-preview guard cannot remain monotonic; if session restore or keyboard or dialog behavior must change; if the production transition contract cannot be exercised by one dependency-free executable harness under `scripts/harness/`; if the harness requires a new dependency or runner, duplicates production transition logic, or expands into broad frontend workflow coverage; if its exact command cannot be reused by Task 29.12; if a framework, build system, fallback path, backend contract change, or UI redesign is required; or if unrelated cleanup cannot be separated into another task.
